## 0. How to use this file

**Rules for every contributor, human or agent:**

1. **Before starting work** — read §2 (milestones) and §3 (task board). Pick a task that is `todo` and whose dependencies are `done`.
2. **When starting** — set the task to `doing` and put your name in Owner.
3. **When finishing** — set to `done`, add the artifact path in Notes, and append a line to §8 (Session log).
4. **When you learn something that changes the plan** — do NOT silently change course. Add an entry to §5 (Decisions) or §6 (Open questions) and flag it.
5. **Never delete a task.** Move it to `dropped` with a one-line reason. The graveyard is evidence.
6. **One task = one reviewable change.** If a task cannot be finished in a single sitting, split it.

**Status vocabulary:** `todo` · `doing` · `blocked` · `review` · `done` · `dropped`

## 1. Guardrails (read before writing any code)

These exist because this project's failure mode is obvious: it is a nine-phase mega-vision, and
mega-visions die in Phase 4 with a beautiful architecture and nothing that runs.

- **Walking skeleton first.** M1 is one thin end-to-end slice, not a layer. No layer gets built to completion before the whole path works badly.
- **One machine before many.** Everything must work against a single machine before it works against the tailnet.
- **Localhost is not a special case.** Every machine — including the one the daemon runs on — is reached over SSH. One code path, forever. The tempting shortcut (spawn `tmux` directly when local) buys a little convenience now and costs two divergent code paths for the life of the project, where the well-tested one is the one that matters least. Decided 2026-07-28; goes into ADR-0005.
- **Orchestrate, don't reinvent.** If a task's description starts to look like "implement SSH/terminal multiplexer/scheduler", stop and re-read the brainstorm.
- **Provisioning is a permanent non-goal.** Yantra adopts machines that already exist; it never creates, images, or destroys them. This is precisely the line that separates it from Coder — and R4's verdict is blunt: *if Yantra ever grows a provisioning layer it becomes a worse Coder and should be deleted.* To be written into ADR-0005 as a non-goal, not left as folklore.
- **One agent first. Do not build the universal adapter.** The vision doc says every agent should behave identically; that is the *destination*, not the starting point. Yantra supports **Claude Code only** in M3 — the one actually installed, with the strongest resume story (`--session-id` presets the UUID, verified in Y-023). A second agent gets added when a second agent is genuinely wanted, and the shared interface is extracted **from two working implementations**, never guessed ahead of one. Owner's framing, 2026-07-28: *"use the cli that we want, not to join everything. If needed we can do it later."*
- **No UI until the CLI is good.** The CLI is the API's first client and its honesty check.
- **No hardware until the software is boring.** Phases 7–9 are a reward, not a shortcut.
- **Test hard.** Every orchestration primitive gets an integration test against a real sshd + real tmux. Mocks lie about SSH. **The fixture is a disposable podman container**, not the host — a separate filesystem, user and network hop make it a more honest stand-in for a remote machine than `ssh localhost`, and it changes nothing about the host's security posture.
- **Rust for the daemon, TypeScript for the web UI** — [ADR-0004](docs/adr/0004-rust-for-the-daemon.md). Chosen for quality and appliance fit over iteration speed, with that trade made explicitly. Rust punishes design churn, so **think before writing**: this is the milestone where the shape is still unknown.
- **Orchestration lives in `yantra-core`, a library crate** — [ADR-0005](docs/adr/0005-core-logic-in-a-library-crate.md). The binaries are thin. The library never prints and never exits, which forces a typed error from the first fallible call instead of an M2 cleanup; M2's daemon changes *where* the code is called from, not *what* it does.
- **Keep SSH, tmux, telemetry and hardware behind narrow traits.** Not to enable a runtime swap any more — to keep the four seams that touch an unreliable outside world fakeable in tests.

## 1b. Invariants discovered by research

Non-obvious rules that research proved the hard way. Violating one of these produces a bug that looks
like something else entirely. **[V]** = verified by execution, **[D]** = documented only.

| # | Invariant | Why | Src |
| --- | --- | --- | --- |
| I-1 **[V]** | Idempotent open is plain `new-session -d` + **treat `duplicate session:` as success**. Do **not** use `new-session -A -d` (broken from a non-TTY daemon) and do **not** use `has-session \|\| create` (TOCTOU race). | The obvious two ways to do this are both wrong. | R2 |
| I-2 **[V]** | Session names restricted to `[A-Za-z0-9_-]`, always addressed as `-t "=name"`. | `:` or `.` in a name makes the session **permanently unaddressable**, and `=` does not rescue it. Targets are otherwise prefix-matched, so `demo` can hit `demo2`. | R2 |
| I-3 **[V]** | Transcripts come from `pipe-pane`, never `capture-pane` polling. Gate arming on `#{pane_pipe}`; cap log size from day one. | `-S -N` is **not** "last N lines", scrollback is unreachable while an agent TUI holds the alternate screen, and passing `-o` twice silently *disables* logging. | R2 |
| I-4 **[V]** | Set `remain-on-exit on` on every agent session. | Without it exit codes are unrecoverable, and **"crashed" is indistinguishable from "finished"**. | R2 |
| I-5 **[V]** | Key machine inventory on `Peer.ID`. HostName is a display label only. | HostName already collides twice in the existing 5-node tailnet. | R1 |
| I-6 **[V]** | LocalAPI requests must send `Host: local-tailscaled.sock` or return 403. | Silent, misleading failure mode. | R1 |
| I-7 **[D]** | Own reboot recovery in Yantra's own store. Do **not** adopt tmux-resurrect/continuum. | They re-run whitelisted commands rather than restore processes, on a 15-minute lossy timer — worse than nothing for an agent session. | R2 |
| I-8 **[D]** | Define the `Multiplexer` interface with **JSON-shaped return types** now, even though only tmux is implemented. | zellij's `subscribe --format json` / `list-panes --json` are genuinely better than tmux's format DSL; a format-string-shaped interface would have to be rewritten. | R2 |
| I-9 **[V]** | **Absence of power-supply data must mean AC, never "unknown".** Desktops have *no* `/sys/class/power_supply/AC*` entry at all; `BAT0/status` reads `Not charging` while on AC; `Win32_Battery` returns **no instances** on Windows desktops. | The naive reading marks every desktop "unknown power" and the battery signal silently mis-scores the most placeable machines in the fleet. | R5 |
| I-10 **[D]** | **If a signal is not in the decision record, it must not influence the decision.** | The explainability contract. `yantra why` is worthless the moment a hidden term can move the outcome. | R5 |
| I-11 **[D]** | Tie-breaks are deterministic: score → static `priority` → name. Explicitly **reject** kube-scheduler's random tie-break. | Reproducibility is the whole point of an explainable placement. | R5 |
| I-12 **[V]** | **Set `busy_timeout` and `journal_mode = WAL` explicitly on every connection open.** Never rely on the binding's default. | Verified across **two independent bindings** — `bun:sqlite` defaults to 0, and `node:sqlite`'s `timeout` also defaults to 0. This is a SQLite-binding trap, not a runtime quirk, so confirm it for `rusqlite` too. Five machines heartbeating every 10 s will otherwise produce intermittent `SQLITE_BUSY` that presents as a network or agent fault. | R6a, R6b |
| I-13 **[D]** | **SQLite calls go through `spawn_blocking`. Keep queries O(small) regardless.** | `rusqlite` wraps a synchronous C API. Called directly from an async task it stalls the tokio worker serving WebSocket terminal streams — the same failure Bun had (a 400 ms query served **0 of 100** concurrent pings), for the same reason, but with a proper fix available. | R6a + ADR-0004 |
| I-14 **[D]** | **No ORM in v1** — `rusqlite` with hand-written SQL. Back up with `VACUUM INTO`. | Yantra's schema is four small tables. Diesel/SeaORM buy migrations and compile-time type-safety we do not yet need, at the cost of build time and indirection. Revisit when the schema stops being trivial. | R6a + ADR-0004 |
| I-18 **[V]** | **The PTY must give the child a controlling terminal**, or `^C` will not work. Verify this explicitly in the `portable-pty` integration test. | Found the hard way in Bun (`new Bun.Terminal()` had exactly this defect). The bug is language-independent and easy to ship unnoticed — an interactive terminal that cannot be interrupted. | R6 |
| I-19 **[V]** | **Never hardcode a `gpiochip` number.** Discover it at runtime. | The Pi 5's RP1 southbridge moved the chip numbering; hardcoded values silently address the wrong chip. | R6 |
| I-20 **[V]** | **Transport is the system `ssh` binary with `ControlMaster` multiplexing** — not a library. **Windows OpenSSH does not support `ControlMaster`** (verified, open since 2019). | Zero library surface to maintain, free `~/.ssh/config` fidelity, and it is what VS Code Remote and JetBrains Gateway both do. Keeps `russh` out of the dependency tree entirely. The Windows gap is another entry on the R-7 pile. | R6, R4 |
| I-21 **[V]** | **`=name` is a valid target ONLY for sessions.** For **window** and **pane** targets it fails outright — `capture-pane -t '=x'`, `send-keys -t '=x'`, `pipe-pane -t '=x'` and `set-option -w -t '=x'` all error with *can't find pane* / *no such window*. Use the trailing-colon form `'=name:'`, or better, capture the stable ids at creation (`%N` pane, `@N` window) and address by those. | Verified twice: in Y-023 (`capture-pane` failed while `list-panes` succeeded on the same live session) and again in Y-031, which found the window case — **`remain-on-exit` is a *window* option, so I-4 cannot be applied with a bare `=name`.** Reproduced on tmux 3.5a and 3.7b. Y-042 would have hit this. | Y-023, Y-031 |
| I-22 **[V]** | **Never pipe an agent's stdout** (`claude ... \| tee`). It destroys TTY detection - Claude Code silently falls into `--print` mode and dies with *"Input must be provided..."*. Log via `pipe-pane`. | Verified in Y-023 by doing exactly this wrong. Reinforces I-3 from a second direction. | Y-023 |
| I-25 **[V]** | **`ssh` cannot report a signal-killed remote command.** It exits 255 with empty stderr and nothing in the log at any verbosity — indistinguishable from a remote `exit 255` and from a dropped multiplexed connection. Carry the status yourself in a sentinel trailer; presence = transport OK, value = command status. | `client_input_channel_req()` in `clientloop.c` handles `exit-status` but has **no `exit-signal` branch**, so `exit_status` keeps its initial `-1` → 255. Verified against OpenSSH master and measured against a real sshd. Y-042 decides create-vs-attach from an exit status, so this would produce duplicate sessions. | R7, Y-041 |
| I-26 **[V]** | **Never build a remote command by joining arguments.** `ssh` space-joins everything after the destination and hands it to the remote *login shell*; `Command::args([...])` gives no protection. Encode the command (base64) so nothing needs quoting. | Verified: `$(id -un)` expands remotely. Workspace `repo` paths come from config files, making this a code-execution path. POSIX `'\''` escaping was also tested and breaks on an embedded newline. | R7, Y-041 |
| I-27 **[V]** | **Killing the local `ssh` does not kill the remote command** — multiplexed or not. It reparents to PID 1. **The stdin-EOF watchdog that was meant to fix this is withdrawn** ([ADR-0008](docs/adr/0008-withdraw-the-stdin-watchdog.md)): it killed every command slower than ~200 ms. The orphan problem is real and currently unsolved — tracked as Y-046. | Measured both ways. The watchdog failure reproduced on the first exec, so multiplexing is not involved, and the same payload against a local shell with a genuinely held-open pipe never fires — the spurious EOF comes from `ssh`. | R7, Y-041, Y-042 |
| I-28 **[V]** | **The `ControlPath` budget is 90 bytes on Linux, 86 on macOS** — not `sun_path`'s 108. The master also binds a 17-character temporary suffix. `%C` costs a fixed 40. Validate at construction. | Measured exactly: 90 works, 91 fails, with two different error messages at two different lengths. Exceeding it otherwise surfaces as an opaque 255. | R7, Y-041 |
| I-29 **[V]** | **Never pass a startup command straight to `tmux new-session`.** A command that exits immediately takes the window, the session and the whole tmux *server* with it before `remain-on-exit` can be set — `set-option` then fails with *no server running*. Create with the default shell, set the option, then `respawn-pane -k` to put the command in the pane. | Measured in Y-042: `new-session -d -s x 'exit 3'` followed by `set-option -w remain-on-exit on` fails outright. A shell does not exit, so the option is always in place before anything can die. The pane's process is then the command itself, which is what makes I-4 able to report how it ended. | Y-042 |
| I-30 **[V]** | **`kill-session` has three "already absent" spellings, not one.** Accept `can't find session`, `no server running` and `error connecting to <socket>` as success. | With no sessions left the tmux server exits, so the *next* kill cannot even connect. Treating that as an error makes teardown fail intermittently depending on what ran before it. | Y-042 |
| I-31 **[D]** | **A test suite of instantaneous commands proves nothing about duration.** Any primitive that wraps a remote process needs at least one test with a command that takes seconds. | Y-041 shipped a watchdog that killed everything slower than ~200 ms and passed CI, because every command in its suite finished in under a millisecond. Found only when Y-042 ran `tmux`, which is merely slow enough to notice. | Y-042 |
| I-32 **[V]** | **A green CI run is not evidence unless it ran on the environment that failed.** GitHub rolls runner images out gradually, so a fix can go green five times on machines that were never broken. Re-run until the job lands on the failing image, and print the versions that matter so you can tell which one you got. | Y-048's fix passed five consecutive runs on image `20260720.247`, which had the working podman. Only the sixth landed on `20260726.254` and actually tested anything. Without the version printout, all six looked identical. | Y-048 |
| I-33 **[V]** | **Never derive a name from `HostName` — use `DNSName`'s first label.** HostName is free text: it collides, and it can contain spaces and non-ASCII. The DNSName label is `[a-z0-9-]`, already satisfies I-2, and is what MagicDNS resolves. This sharpens I-5, which called HostName merely "a display label". | In the live 6-node tailnet HostName collides **twice** (`localhost` for both iOS devices, `LAPTOP-9ML3D644` for both sides of one dual-booted laptop) and the MacBook's is `Bishwajeet’s MacBook Pro` — spaces plus U+2019, a Unicode right single quote. As a tmux session name that breaks I-2; in a remote command it is a quoting bug wearing a disguise. | Y-022 |
| I-34 **[V]** | **The environment an SSH command runs in is not the environment you get when you log in.** Resolve remote tool paths absolutely; never rely on the remote `PATH`. | On the MacBook `ssh mac 'command -v tmux'` finds nothing: the non-interactive `PATH` is `/Users/<user>/.cargo/bin:/usr/bin:/bin:/usr/sbin:/sbin:…` with no `/opt/homebrew/bin`, which is where Homebrew installs. `tmux 3.7b` is sitting at `/opt/homebrew/bin/tmux` the whole time. The same gap hides Ghostty's terminfo. Interactively everything works, so this presents as "the install failed". | Y-049 |
| I-35 **[V]** | **The base64 → `/bin/sh` envelope also shields `=name` from the remote login shell.** Never bypass it, not even for a throwaway command. | The MacBook's login shell is `/bin/zsh`, where `=word` is filename expansion. `tmux kill-session -t =yantra-probe` sent through it returns `zsh:1: yantra-probe not found` — the session survives and the caller thinks it was killed. The identical argument through the envelope succeeds. I-26 justified the envelope by space-joining alone; this is the second and sharper reason. | Y-049 |
| I-36 **[V]** | **tmux aborts if the outer `TERM` has no terminfo entry on the machine running tmux.** Pin a conservative `TERM`; never propagate the client's. | `TERM=xterm-ghostty tmux attach` gives `missing or unsuitable terminal: xterm-ghostty` on any host lacking that entry — which was both `cachyos-g14` and the MacBook, despite Ghostty being the terminal in daily use. Non-interactive `ssh host 'cmd'` does not forward `TERM` (it arrives unset), so ADR-0006's command path is immune; the PTY paths are not, which means `attach` today and M6's browser terminal later. The client's terminal is unbounded — any emulator a user happens to run — so it can never be trusted as an input. | Y-049 |
| I-37 **[D]** | **macOS provides no `XDG_RUNTIME_DIR` and a ~52-character `TMPDIR`.** | `TMPDIR` is `/var/folders/<2>/<26>/T/`. Against I-28's 86-byte `ControlPath` limit that leaves roughly 34 bytes for the socket name. `up::state_dir()` prefers `runtime_dir()`, which macOS does not provide, so a daemon running there falls back to the long path. Harmless while the daemon runs on Linux — `ControlPath` measured 27 bytes — but it would surface as a truncated path, not as a clear error. | Y-049 |
| I-38 **[V]** | **A machine's own MagicDNS short name is not its tailnet address.** | `getent hosts cachyos-g14` returns `127.0.1.1`: `/etc/hosts` shadows MagicDNS for the local hostname. Self-dialling also never traverses the WireGuard path, so `tailscaled`'s port-22 interception is never reached and a self-directed `ssh` gets `Connection refused`. A workspace that names the local machine therefore fails looking like a network problem. | Y-049 |
| I-39 **[V]** | **`LastSeen` says nothing about whether a peer is reachable.** Read `Online`; treat the zero time as absent. | Tailscale's own doc comment in `ipn/ipnstate` says `LastSeen` is *"only present if offline"*, and the live tailnet disagrees on both halves: on 1.98.9 the **online** MacBook carries a real `2026-07-29T22:10:00.1Z`, while `Self` — also online — carries the Go zero time `0001-01-01T00:00:00Z`. So a present value does not imply offline, and a zero value does not mean never seen. Also peer-only: `Expired` exists on peers and not on `Self`, and **two of six nodes here have expired keys**, which makes "offline" and "unusable" different states. | Y-050 |
| I-40 **[V]** | **`default-terminal` is a *server* option — never set it.** `set-option -t '=session'` accepts the target and applies the value to the whole tmux server. | Setting `default-terminal screen` on `=ours` changed the value reported for an unrelated `=theirs` **and** for `show-options -s`, and a fresh pane in `theirs` came up with `TERM=screen`. Reproduced on tmux **3.5a** (Alpine) and **3.7b** (Arch and macOS 26.5.1). So a per-session setting silently reconfigures tmux for every session on the machine, including the owner's own — and buys nothing: the built-in default is already `tmux-256color`, which is present in the terminfo database on all three systems. The `TERM` that matters is the **outer** one at attach time, not the session's. | Y-053 |
| I-41 **[V]** | **tmux has two spellings for "no server", and one is shared with real failures.** Match the reason in brackets, never the verb. | `ECONNREFUSED` (stale socket) prints `no server running on <path>`; a socket that never existed prints `error connecting to <path> (No such file or directory)`. But `error connecting to <path> (Permission denied)` — a **live** server behind an unreadable socket — uses the same verb, and **every one of them exits 1**, so the exit code carries no information. Reproduced on tmux 3.7b by `chmod 000` on the socket of a running server. Swallowing the third made `kill` return `Ok(())` on a failure. | Y-057 |
| I-42 **[V]** | **tmux rewrites control characters in `-F` output, and not identically across versions.** Never delimit format fields with a tab. | The same format string `A\tB|C#{session_name}` yields `A_B|Calpha` on **tmux 3.5a** (Alpine) and `A\tB|Calpha` on **3.7b** (Arch, macOS). `|` survives both. This matters beyond the delimiter: **CI runs 3.5a while both real machines run 3.7b**, so format-string behaviour differs between CI and production. It failed in the safe direction here — the older tmux is the one CI runs, so it broke loudly instead of passing in CI and failing on the fleet. | Y-054 |
| I-43 **[V]** | **`infocmp` does not always answer for the terminfo database tmux reads.** A machine can hold two, and asking the wrong one is a needless downgrade — so bias the probe toward falling back, never toward asserting an entry exists. | On the MacBook, `/opt/homebrew/bin/tmux` links Homebrew's `libncursesw` and reads `/opt/homebrew/opt/ncurses/share/terminfo`, while `/usr/bin/infocmp` is Apple's ncurses **6.0 from 2015** reading only `/usr/share/terminfo`. Measured across 11 terminals: **3 disagree** (`alacritty`, `foot`, `wezterm` — absent to `infocmp`, accepted by tmux) and **0 disagree the other way**. So the error is always a fallback that was not needed, never an attach that aborts. `yantra fix-terminfo` settles it regardless: `~/.terminfo` is read by both. Also learned here: **tmux only checks the terminal when it has a pty** — without `ssh -t` an unknown `TERM` produces no complaint at all, so any test of I-36 that forgets the pty proves nothing. | Y-058 |
| I-44 **[V]** | **On macOS a process launched over SSH cannot read the login keychain — and that is where Claude Code keeps its account token.** An agent started that way comes up *not logged in*, and the keychain call that caused it says nothing at all. | An ssh session lands in launchd's **`Background`** domain (`launchctl managername`), not `gui/<uid>`, so every keychain call returns *User interaction is not allowed* — even `show-keychain-info`. `security find-generic-password -s "Claude Code-credentials" -w` exits **36 with zero bytes on stdout *and* stderr**, the same shape of silence as I-25; the item's **metadata reads fine**, so an existence check passes while the read fails. Claude Code 2.1.220 itself renders `Not logged in · Please run /login` and suggests `security unlock-keychain`, which needs a password and therefore cannot be Yantra's answer (B4). **Linux is unaffected** — the token is a plain `~/.claude/.credentials.json` (`claudeAiOauth`, mode 600), which is why Y-023 saw none of this. | Q12 |
| I-24 **[D]** | **Validate a workspace name before it becomes a path.** Reject empty, leading-dot, `..`, `/`, `\` and NUL. The same rule applies to anything else user-supplied that is joined to a directory or interpolated into a remote command. | Names arrive from `yantra up <name>` and are joined to the workspaces directory. Without the check, `yantra up ../../etc/passwd` reads that file and reports a TOML error, which is both a disclosure and a confusing message. Y-041/Y-042 raise the stakes: the same string will reach a remote shell. | Y-040 |
| I-23 **[V]** | **Pre-seed `hasTrustDialogAccepted` before launching Claude Code in a new directory** - `~/.claude.json` -> `projects.<abs-path>`. | On first run in an unseen directory the TUI opens a *trust this folder* dialog that **silently swallows keystrokes**: an automated `send-keys` prompt is typed into the dialog and Enter answers it. Presents as the agent ignoring you. | Y-023 |

- **2026-07-30 (cont. 10)** — **Y-058 done, and M2 with it.** The terminal question is answered by probing, never by a list of terminals to support: pass the client's `TERM` through when the far side has an entry, fall back to one floor when it does not, and install on request via **`yantra fix-terminfo <machine>`**. All three modes ship without a config knob. Installing stayed *explicit* on purpose — it writes to someone's `$HOME`, which should be asked for rather than happen as a side effect of attaching — and `tic` lands in `~/.terminfo`, so it never wants root. **The objection that nearly killed the install path was wrong, and checking took one command:** Alpine has no `tic` in the base image, so CI could only have tested degradation — but `apk add ncurses` supplies it, verified by a full `infocmp | tic` round trip as a non-root user before any code was written. That one line is the difference between a tested feature and a manually-tested one. **Two findings, both from the live check rather than the container.** The MacBook's `/opt/homebrew/bin/tmux` links Homebrew's `libncursesw` and reads a *different terminfo database* than `/usr/bin/infocmp`, which is Apple's ncurses 6.0 from 2015 — measured across 11 terminals, 3 disagree and all 3 in the safe direction, so the probe under-reports rather than promising an entry that is not there (**I-43**). And **tmux only checks the terminal when it has a pty**: the first live check reported "can't find session" for `definitely-not-a-terminal` just as happily as for a real one, and only `ssh -tt` exposed the difference — an I-36 test without a pty proves nothing. Also verified across a ten-year ncurses gap: `infocmp -x` from 6.6 compiled under 6.0 with a warning and exit 0, macOS laying the result out in hex directories. `TERM` is an environment variable that reaches a remote command, so it is validated against a conservative alphabet, with a container test asserting that an injection never lands. 81 tests, 4 skipped.
- **2026-07-30 (cont. 11)** — **Y-047 closed by deleting the field ([ADR-0010](docs/adr/0010-drop-branch-from-the-workspace-schema.md)).** `branch` was parsed into `Workspace`, asserted on by two parse tests, and read by nothing for the whole of M1 and M2 — the same species of contradiction ADR-0009 closed for `machine`, and the last one on the board. **The recorded question was the wrong one twice.** It was framed as refuse/stash/warn under a dirty worktree, but *when* decides more than *what*: `up` returns `Created` or `Attached`, and a checkout under an `Attached` session rewrites the tree beneath whatever is running there — a live agent, once M3 exists — so it could only ever be a creation-time act, where the tree is not yet in use. And the *what* was moot anyway, because **checkout semantics break the case M3 makes ordinary**: two workspaces may name the same `repo` on the same `machine`, one directory holds one branch, so two agent workspaces on one clone fight and the last to open wins. `git worktree` does not have the problem. Building checkout semantics would have meant building something M3 replaces, so the field is gone and branch selection returns as worktrees when M3 states its requirements. `deny_unknown_fields` — ADR-0007's own principle, that a silently ignored key is the worst kind of bug — makes a stale file fail loudly and name the field, which is the entire migration; verified against the real CLI. Cost was zero: no workspace files existed on disk. 82 tests, 4 skipped.
- **2026-07-30 (cont. 12)** — **M3 opened by paying Q12 first, and Q12 did not get to ask its question.** The plan was the cheap one: re-run the Y-023 spike on the MacBook now that the machine is reachable, confirm R-1 stays refuted on the OS the bug was actually filed against, then build. Claude Code **2.1.220** — the same build the Linux spike ran, so the version is controlled — came up in a tmux session that was detached from creation and never attached, took a prompt, and answered **`Not logged in · Please run /login`**. **The token is in the macOS login keychain and an ssh session cannot read it** (**I-44**): `launchctl managername` reports `Background` rather than `gui/<uid>`, and every keychain call from there returns *User interaction is not allowed*. The read is silent in the I-25 sense — `security find-generic-password -s "Claude Code-credentials" -w` exits **36 with zero bytes on stdout and stderr** — while the item's *metadata* reads fine, so an existence check passes and only the read fails. Claude Code's own suggestion is `security unlock-keychain`, which wants a password and so cannot be Yantra's answer (B4). Linux never sees this: the token is a plain `~/.claude/.credentials.json`, which is exactly why Y-023 was clean and exactly the transfer Q12 suspected. **So R-1 remains untested on macOS**, now behind Y-059 rather than beside it — but two useful facts came out anyway: the transcript **is** created and written while fully detached on macOS (57,841 bytes, `session_attached=0` throughout), so the file-write path is not the suspect; and the cheapest remedy is untested rather than unavailable — a tmux server started from the **GUI** session should inherit keychain access, and `launchctl asuser` wanting root is the only reason that could not be checked from here. Recorded as **R-21**, which displaces R-7 as top risk because it costs a machine in daily use rather than a hypothetical one. M3's board written: Y-059 (the blocker), Y-060 `--agent claude`, Y-061 `logs`, Y-062 `down`, Y-063 finished-vs-crashed. Y-046 stops being theoretical here — an agent session is the first long-running remote process. The Mac was left as found: session killed, scratch directory and its transcript removed, `~/.claude.json` restored from the backup taken before the trust-dialog seed (I-23).
- **2026-07-30 (cont. 13)** — **Q7 closed after eight months of being the recorded prior: [ADR-0011](docs/adr/0011-claude-code-runs-as-a-tui-in-tmux.md), TUI in tmux, one path.** R3's verdict was *"all five are safer driven headless"*, and the tracker has carried "tmux is the human view, headless is what Yantra automates" ever since. **Overruled on evidence R3 did not have.** Its three hazards were Gemini's TTY-loss exit, OpenCode's tmux corruption, and Claude Code #63545 — the first two belong to agents the one-agent-first guardrail says Yantra does not ship, and the third did not reproduce in Y-023. What remains is a cost with no matching benefit: `claude -p` leaves nothing to attach to, so the automation channel and the human channel would be two processes or a reconstructed TUI, and attaching from another machine mid-run is the thing the project is named for. Re-reading R3 for the ADR turned up three things the board had not been using: **`claude agents --json`** prints `{pid, sessionId, cwd, status}` with **no TTY required**, which is free process↔session correlation and pushes Y-044 back another milestone; **`claude auth status`** emits `loggedIn` as JSON, which turns I-44 from a silent useless session into a refusal that names its reason, so the ADR makes it a pre-launch gate; and `claude` has **no cwd flag**, so `cd <repo> &&` is not a stylistic choice. The ADR deliberately leaves one thing unbuilt: whether Yantra ever *sends input* to the agent. Nothing in M3 needs it — `up`, `logs` and `down` are launch, read and stop — and `send-keys` into a TUI is the brittle part, with I-23 as the scar. Y-060 is therefore **not** blocked by Y-059: it builds and tests on Linux, where the container and `cachyos-g14` both work, and macOS joins when the keychain question is answered.
- **2026-07-30 (cont. 14)** — **Y-060 done: `yantra up <name> --agent claude`.** `yantra_core::agent` is deliberately shaped like `tmux::Tmux` — resolve a path once per connection, hold it, no cache key — with one departure that matters: **its candidate list includes `$HOME` and tmux's deliberately does not.** tmux's stated reason is that a `$HOME` install is on `PATH` by construction; for Claude Code that is simply false, because the installer writes to `~/.local/bin` and adds it to `PATH` by editing a shell rc file that a non-interactive ssh session never reads. `ssh <mac> 'command -v claude'` answers nothing while the binary sits right there — **I-34 for the third time, and the first where an existing assumption in our own code was the thing that was wrong.** Everything an agent needs is settled before tmux is touched, so a refusal leaves nothing half-open; that ordering is what makes the **`auth status` gate** worth having, and it was verified end to end against the real MacBook: `up --agent claude` refuses and names the keychain, while the same `up` without the flag still opens a session normally. **I-23 turned out to need no code, and that is a consequence of ADR-0011 rather than an oversight** — the trust dialog swallows *automated* keystrokes, and Yantra sends none; the hazard returns the day something drives the agent. `--agent` alongside a workspace `startup` is refused rather than resolved, because picking a winner would silently ignore an instruction and ADR-0007's rule does not stop applying when the instruction arrives on the command line. **The tests are honest about their limit:** five container tests run against a *stub* `claude`, every output shape copied from executed 2.1.220 including the exact negative JSON the Mac produced under I-44 — which tests Yantra's orchestration for real and says nothing about the binary. The reality check needs a machine that is both reachable and authenticated, and there is not one: `cachyos-g14` cannot ssh to itself (I-38) and the MacBook cannot log in (I-44). **So Y-059 blocks more than macOS — it is the only route to a real-agent test at all**, which is now recorded on its row. One test was wrong before it was right: the injection unit test searched for `; rm -rf ~; ` in the output, which the *correctly* escaped string also contains, inside quotes. Substring hunting cannot tell safe from unsafe here, so it became an exact-match assertion plus a container test that runs the thing on a real `/bin/sh` and checks the canary was never touched. 93 tests, 4 skipped.
